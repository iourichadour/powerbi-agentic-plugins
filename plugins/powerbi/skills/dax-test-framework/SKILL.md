# DAX Test Framework — Dual-Profile Execution Skill

This skill runs `.dax` DAX Query View test files — hand-authored or generated by
[`dax-unit-testing`](../dax-unit-testing/SKILL.md) — against either a local Power BI Desktop
instance (`DEV`) or a deployed Fabric semantic model (`CLOUD`), using one shared transport,
discovery, and reporting implementation across three entry points (CLI, pytest, notebook).

For the `pql-tester` agent that orchestrates this alongside the measure-certification registry,
see [`plugins/powerbi/agents/pql-tester.agent.md`](../../agents/pql-tester.agent.md).

## Prerequisites

- **`uv`** and **ADOMD.NET transport** (Windows only, `pythonnet`/`pyadomd` declared in
  [`pyproject.toml`](pyproject.toml)) are provisioned automatically by `setup-team-plugins.ps1`
  whenever the `powerbi` plugin is installed — no admin rights required. `uv run` resolves
  `pyproject.toml` dependencies without polluting a global environment (or pass
  `--project plugins/powerbi/skills/dax-test-framework` from elsewhere). If a project needs a
  non-standard ADOMD.NET location, set the `ADOMD_DIR` environment variable to override discovery.
- **DEV profile**: Power BI Desktop must have this project open (the tabular engine port is
  discovered dynamically — see [Desktop port discovery](#dev-profile-power-bi-desktop)).
- **CLOUD profile**: a Fabric service principal with access to the target workspace/semantic model,
  and the five `PBI_*` environment variables set (see [Credential hygiene](#credential-hygiene)).
- **PQL.Assert deployed** in the target model — run `pql-tester setup` (or
  `dax-unit-testing/assets/scripts/setup_project.py`) once per project if it hasn't been. The
  [smoke gate](#smoke-gate) fails fast with a clear message if it isn't.

## DEV vs. CLOUD Profiles

| | `DEV` | `CLOUD` |
|---|---|---|
| Target | Local Power BI Desktop | Deployed Fabric semantic model (XMLA endpoint) |
| Connection | Dynamic port discovery (see below) | `PBI_WORKSPACE`/`PBI_MODEL`/`PBI_CLIENT_ID`/`PBI_TENANT_ID`/`PBI_CLIENT_SECRET` |
| Use for | Local iteration while authoring measures/tests | CI, scheduled runs, post-deployment verification |

### DEV profile: Power BI Desktop

`dax_test_helpers.discover_desktop_port()` scans
`%LOCALAPPDATA%\Microsoft\Power BI Desktop\AnalysisServicesWorkspaces\*\msmdsrv.port.txt` (UTF-16)
and picks the **newest** file by modification time — never a hard-coded port — so it works
correctly even with multiple Desktop instances open. If Desktop isn't open, this fails with
`CONNECTION_ERROR` before attempting anything else.

### CLOUD profile: Fabric XMLA

Reads exactly five environment variables and never anything else:
`PBI_WORKSPACE`, `PBI_MODEL`, `PBI_CLIENT_ID`, `PBI_TENANT_ID`, `PBI_CLIENT_SECRET`. If any are
missing, the framework reports **only the missing variable names** — it never attempts a partial
connection, and never prints or logs the values of any of them (including on failure).

## Smoke Gate

Before running the requested suite, the framework always executes one PQL.Assert smoke assertion
(`PQL.Assert.ShouldBeTrue("Smoke Test", TRUE())`). This distinguishes three failure modes before
any suite assertions are reported:

1. **`CONNECTION_ERROR`** — could not connect at all (Desktop not open / bad CLOUD credentials).
2. **`DAX_ERROR`** — connected, but the smoke query itself failed — almost always because
   PQL.Assert isn't deployed to this model yet. Run `pql-tester setup` first.
3. **Smoke assertion returned but did not pass** — also treated as a stop condition; something is
   wrong with the library deployment even though the connection and query succeeded.

If the smoke gate fails, the run stops immediately — the rest of the suite is never silently
reported as failed assertions, so a missing-library problem is never confused with real test
failures.

## Discovery and Filters

- Discovers root-level `*Tests.dax` and `*Test.dax` files in the target `DAXQueries/` folder.
- Excludes scratch queries matching `Query <N>.dax` (Desktop's default DAX Query View tabs).
- `--file <substring>` — case-insensitive filename substring filter (e.g.
  `--file "MeasureCertification.ANY.Business"` targets one generated certification suite).
- `--environment {ANY,DEV,PROD}` — independent filter against the filename's environment token
  (`[Area].[Environment].Test(s).dax`). Omit to run every discovered file regardless of tag. If
  the filter matches zero files, the framework reports the available tokens and a non-zero exit
  code rather than silently reporting "0 ran, 0 failed" as success.

## Entry Points

All three share `dax_test_helpers.py`'s discovery, smoke gate, and result-parsing logic, so a
suite behaves identically no matter which one runs it.

### CLI

```powershell
uv run --project plugins/powerbi/skills/dax-test-framework `
  plugins/powerbi/skills/dax-test-framework/scripts/run_dax_tests.py `
  --profile DEV --model-dir "<project>/DAXQueries" --reports-dir reports
```

Add `--file <substring>` and/or `--environment {ANY,DEV,PROD}` to target a subset. Exits `0` only
when every selected assertion passed and no query/connection errors occurred.

### Pytest wrapper

```powershell
uv run --project plugins/powerbi/skills/dax-test-framework pytest `
  plugins/powerbi/skills/dax-test-framework/scripts/test_dax_suite.py `
  --dax-profile CLOUD --dax-model-dir "<project>/DAXQueries"
```

See [`scripts/conftest.py`](scripts/conftest.py) for the full `--dax-*` option list. The smoke
gate runs once per session (a `dax_transport` session fixture) and fails the whole session via
`pytest.fail` if it doesn't pass.

### Notebooks

[`assets/notebooks/dax_tests_dev.ipynb`](assets/notebooks/dax_tests_dev.ipynb) and
[`dax_tests_cloud.ipynb`](assets/notebooks/dax_tests_cloud.ipynb) are clean templates: every cell
makes its configuration explicit (profile, `DAXQueries` path, filters) rather than assuming a
specific model. Copy the relevant notebook into a target project and fill in
`MODEL_DAX_QUERIES_DIR` before running. Both use the exact same `dax_test_helpers`/`run_dax_tests`
functions as the CLI.

## Credential Hygiene

- CLOUD credentials come **only** from the process environment — never a config file, never a
  CLI argument, never a notebook cell value.
- No entry point prints, logs, or writes `PBI_CLIENT_SECRET` (or any of the other four variables)
  to console output, JUnit XML, Markdown, or `coverage.json`/`coverage-summary.md`.
- Set them in your shell or a secret store (Key Vault, CI secret) immediately before invoking a
  CLOUD run, and avoid `.env` files committed to source control.

## Report Interpretation

Every run writes `reports/junit.xml` and `reports/failures.md`. Both use the same fixed,
machine-readable error-type vocabulary shared with `dax-unit-testing` (`VALUE_MISMATCH`,
`BLANK_RESULT`, `DAX_ERROR`, `MEASURE_NOT_FOUND`, `CONNECTION_ERROR`, etc. — see
[`../dax-unit-testing/references/certification-registry-schema.md`](../dax-unit-testing/references/certification-registry-schema.md#error-type-vocabulary)
for the full list) so a CI gate can branch on error type without parsing prose.

- `junit.xml` — one `<testsuite>` with one `<testcase>` per assertion; failures/errors carry the
  error type as the `type` attribute.
- `failures.md` — a table of only the failing assertions, for a quick PR-comment-friendly summary.

## Viewing Results: `dax-test-dashboard.html`

Open [`assets/dax-test-dashboard.html`](assets/dax-test-dashboard.html) to review a run visually.
It fetches `reports/junit.xml` (relative to the HTML file, cache-busted) at load time and on
**Refresh results** — it never embeds test data in the HTML itself, so the same file works across
runs and projects.

- **Serve locally** — browsers block a directly-opened (`file://`) page from fetching an adjacent
  file. Serve the folder containing the dashboard and its `reports/` directory, e.g.:
  ```powershell
  python -m http.server --directory plugins/powerbi/skills/dax-test-framework/assets
  ```
  then open `http://localhost:8000/dax-test-dashboard.html`.
- **Local file picker fallback** — if automatic fetch fails (blocked by `file://` origin rules, or
  no server running), the dashboard shows why and lets you pick one or more local XML files with
  **Open local XML…** instead.
- Supports both a bare `<testsuite>` (CLI runner shape) and a `<testsuites>`-wrapped document
  (pytest shape) — see [`assets/samples/`](assets/samples/) for one sanitized example of each,
  plus a sample Markdown failure summary.

## Generated Certification Suites

A suite generated by `dax-unit-testing/assets/scripts/generate_measure_tests.py` (e.g.
`MeasureCertification.ANY.Business.Tests.dax`) follows the same root-`DAXQueries/`,
`[Area].[Environment].Test(s)` naming and `UNION`-of-assertions contract as a hand-authored suite,
so every entry point here discovers and runs it automatically — no second execution path needed.
