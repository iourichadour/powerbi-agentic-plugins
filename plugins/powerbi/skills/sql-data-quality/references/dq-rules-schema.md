# dq_rules.csv — Rules Registry Schema (T-SQL Edition)

**Role in SQL Data Quality Framework:**  
This CSV is the **single source of truth for all validation rules** — both auto-generated by schema inspection and manually authored. The registry drives:
1. `Generate-DQRulesCSV.ps1` — schema inspection + pattern matching
2. User review & approval (Step 3–4)
3. `Generate-DQAuditView.ps1` — T-SQL code generation (one CASE expression per rule)
4. Power BI report pages (rule inventory, coverage, severity filtering)

Use this CSV as the editable, version-controlled registry of data quality rules.

---

## Required Columns

```csv
RuleId,TableName,ColumnName,RuleType,ExpectedType,AllowBlank,MinValue,MaxValue,AllowedValues,RefTable,RefColumn,ConditionSQL,Severity,Notes
```

All 14 columns must be present even if some rows are blank.

---

## Field Meanings

| Column | Type | Required | Description | SQL Pattern |
|--------|------|----------|-------------|------------|
| **RuleId** | string | ✓ | Unique rule identifier (e.g., `FD_LoanID_KeyNotBlank`) | Used as temp comment in VIEW DDL |
| **TableName** | string | ✓ | Source table name (e.g., `FactLoan`) | Determines which VIEW this rule applies to |
| **ColumnName** | string | ✓ | Column to validate (e.g., `LoanID`) | Drives flag column name: `[ColumnName]_[RuleType]` |
| **RuleType** | string | ✓ | Rule category: `KeyNotBlank \| KeyUnique \| RI \| TypeNumber \| TypeDate \| Domain \| Range \| Duplicate \| Custom` | Determines which CASE pattern in `sql-check-patterns.md` |
| **ExpectedType** | string | | Power BI data type label (e.g., `Text`, `Number`, `Date`, `Boolean`). Used for model inventory coverage reporting. | Used in DAX coverage measure |
| **AllowBlank** | 0/1 | | If `1`, nulls/blanks bypass this rule (pass). If `0` (default), nulls fail the check. | Affects CASE logic: `OR src.[Col] IS NULL THEN 0` (pass) vs `AND src.[Col] IS NOT NULL` (fail if null) |
| **MinValue** | number | | Min boundary for Range rule (e.g., `100`). | Used in CASE `BETWEEN @Min AND @Max` |
| **MaxValue** | number | | Max boundary for Range rule (e.g., `9999999`). | Used in CASE `BETWEEN @Min AND @Max` |
| **AllowedValues** | string | | `\|`-delimited list of allowed values (e.g., `Prospecting\|Approved\|Closed Won`). For Domain rules. | Used in CASE `IN (N'Prospecting', N'Approved', N'Closed Won')` |
| **RefTable** | string | | Reference table name for RI checks (e.g., `DimOriginator`). | Drives `NOT EXISTS (SELECT 1 FROM [dbo].[RefTable] WHERE ...)` |
| **RefColumn** | string | | Reference column name in RefTable (e.g., `OriginatorID`). | Joins FK to reference table PK |
| **ConditionSQL** | string | | Optional T-SQL WHERE clause for conditional rules (e.g., `src.[Stage] = 'Closed Won'`). If blank, rule applies to all rows. | Wraps CASE: `CASE WHEN (ConditionSQL) THEN (flag expression) ELSE 0 END` |
| **Severity** | string | ✓ | `Error` (critical) or `Warn` (quality concern). Used to populate `MaxSeverity` column in audit VIEW. | Drives conditional formatting in Power BI; Error > Warn > NULL |
| **Notes** | string | | Custom notes for audit trail (e.g., `"Composite key: AssetID, YearBuilt"`). | Visible in Power BI report; aids troubleshooting |

## Authoring Notes

- **Auto-generated vs manual:** Rows generated by `Generate-DQRulesCV.ps1` have `Notes = "Auto-detected"`. User can edit or delete these rows before approval.
- **Severity assignment:** Automatically suggested — `Error` for PKs/FKs, `Warn` for type/range/domain checks. User can override (Step 3).
- **AllowedValues delimiter:** Use `|` (pipe), not comma (to avoid CSV parsing issues). Whitespace is preserved, so `Prospecting|Approved|Closed Won` is OK.
- **RuleId uniqueness:** Not enforced in CSV, but convention is `{TableName}_{ColumnName}_{RuleType}` or similar for readability.
- **Blanks in optional columns:** OK to leave `MinValue`, `MaxValue`, `AllowedValues`, `RefTable`, `RefColumn`, `ConditionSQL` blank if not applicable to that rule type.

## Usage in SQL Data Quality Framework

### Schema Inspection (Step 2)
`Generate-DQRulesCSV.ps1` reads table schema and outputs CSV rows:
- PK columns → `KeyNotBlank` + `KeyUnique` rows (Severity: Error)
- FK columns → `RI` rows (Severity: Error)
- Numeric columns (`FLOAT`, `INT`, `DECIMAL`) → `TypeNumber`, `Range` rows (Severity: Warn)
- Date columns (`DATE`, `DATETIME`) → `TypeDate` rows (Severity: Warn)
- Varchar columns with low cardinality (< 20 values) → `Domain` rows (Severity: Warn)
- Non-nullable text → `KeyNotBlank` rows (Severity: Warn)

### User Approval (Steps 3–4)
User reviews CSV, edits rows, adds custom rules, and explicitly approves before proceeding.

### VIEW Generation (Step 5)
`Generate-DQAuditView.ps1` reads approved CSV and generates T-SQL:
- Per rule: switch on `RuleType` → emit CASE expression
- `ConditionSQL` → wrap rule in outer CASE
- Combines all flags into `RowHasIssues` (CASE WHEN f1=1 OR f2=1 OR ... THEN 1 ELSE 0 END)
- Combines severity into `MaxSeverity` (picks highest triggered rule severity: Error > Warn > NULL)
- Concatenates flag names into `IssueList` (STUFF + CASE pattern)

### Power BI Reporting (Steps 6–7)
Import audit VIEW into Power BI; create pages:
- **Exceptions page:** Filter `RowHasIssues = 1`; display `IssueList` + `MaxSeverity`; color-code by severity
- **Coverage page:** Join CSV to model columns; show rule count by table/type/severity
- **Drill-through:** PK columns passed through VIEW enable drill-down from summary metrics to individual records
